# Known Gaps and Risks

## Classification key

- **Observed**: directly verified in the codebase or test suite
- **Inferred**: reasonably deduced from code structure and patterns
- **Needs confirmation**: uncertain, requires investigation

## Language features

### Not yet implemented

| Feature | Parse status | Execution status | Risk |
|---------|-------------|-----------------|------|
| General-purpose `CALL` | Parsed to AST | Only documented `db.index.vector.*` and `db.index.fulltext.*` procedures are supported; other procedures return an unsupported-feature error | Low — clear error |
| General-purpose `CALL ... YIELD` | Parsed to AST | The index query procedures compose as clauses (`CALL ... YIELD ... MATCH ...`); other procedures return an unsupported-feature error | Low — clear error |
| `LOAD CSV` | Not in grammar | N/A | Low |
| `USE <graph>` (multi-database) | Not in grammar | N/A | Low |
| `EXPLAIN` / `PROFILE` (Cypher keywords) | Not in grammar | API-only | Low — exposed as `db.explain()` / `db.profile()` API methods rather than Cypher syntax. `PROFILE` runs the query for real (including writes); `EXPLAIN` is plan-only. |
| Quantified path patterns | Not in grammar | N/A | Low — future openCypher syntax |
| Inline `WHERE` inside variable-length relationship | Not in grammar | N/A | Low — parse error |
| Type mismatch detection between comparable types | Accepted | Compared without error; `<`, `>`, `<=`, `>=` give `null`, as in Cypher | Low — 1 ignored test |
| Parameter as a label or relationship type | N/A | Not implemented | Low — not standard Cypher |
| Vector ANN execution is opt-in | N/A | Vector indexes use exact flat scans over the indexed scope by default; an HNSW index is built with ``OPTIONS {indexConfig: {`vector.indexProvider`: 'hnsw'}}`` (`lora-store/src/memory/hnsw.rs`, `tests/vector_index.rs`) | Low — flat is exact and fine for small corpora; choose HNSW for production-scale semantic retrieval |
| List-of-`VECTOR` as a property | Parsed | Rejected at write time (`PropertyConversionError::NestedVectorInList`) | Low — loud error; shape decision to keep future indexing viable |

## Storage and data integrity

> 🚀 **Production note** — The gaps in this section (operator controls,
> scoped index coverage, and transaction isolation behavior) are by design
> for the in-memory core. They are addressed in the [LoraDB managed
> platform](https://loradb.com) — use the table below to decide whether a
> self-hosted deployment is viable, or whether the managed option is the
> better starting point.

| Gap | Classification | Risk |
|-----|---------------|------|
| WAL/operator controls are not uniform across surfaces | Observed | **Low–Medium** — Rust and `lora-server` expose explicit checkpoint/status/truncate controls. Node, Python, Go, and Ruby can open filesystem-backed WAL databases; WASM remains snapshot-only. See [WAL](../operations/wal.md). |
| Constraint/index coverage is scoped | Observed | **Medium** — uniqueness, existence, type, key, RANGE, TEXT, POINT, LOOKUP, VECTOR, and FULLTEXT surfaces exist; composite multi-property seeks are still absent, and ANN vector execution (HNSW) is opt-in per index |
| Transaction isolation is conservative | Observed | **Medium** — auto-commit writes publish optimistically under a writer mutex; explicit read-write transactions (including interactive `db.begin()` transactions in the Node binding) hold the writer lock for their full lifetime, so other writers wait; read-only transactions pin snapshots |
| A second in-process open of a database directory shares the open engine | Observed | Low — both handles talk to one engine and one WAL writer, never two; a second *process* gets `LORA_LOCKED` |
| Node / relationship IDs are never reused | Observed | Low — `u64` counter will not overflow in practice |
| Tombstones and clone-heavy compatibility APIs | Observed | **Low–Medium** — deleted IDs leave slot gaps; hot executor paths use borrow closures, but `all_nodes()` and other record-returning scans still allocate |

## Query correctness

| Issue | Classification | Risk |
|-------|---------------|------|
| `toLower` / `toUpper` are not locale-aware | Observed | Low — Unicode case mapping is supported, locale-specific folding is host-side |
| `round()` returns an integer for integral results and rounds half away from zero | Observed | Low — Neo4j returns a float |
| Float comparison uses IEEE 754 | Observed | Low — `NaN != NaN` is standard |
| lora-graphql: a `@unique` (non-key) value held by a node the caller cannot read is reported as taken on create and update | Observed | Medium for fields whose use must stay private (an email). Keys are covered: a create under a hidden key answers as under a free one (G-20, `docs/design/graphql-threat-model.md`). Key such a field, or leave `@unique` off it |
| `<`, `<=`, `>`, `>=` between two temporals of different types (a `DATE` and a `DATETIME`) is an error, including when a RANGE index answers the predicate | Observed | Low. A deliberate divergence: Cypher gives `null`, which made `WHERE d >= date()` over `DATETIME` values drop every row silently (E-1). A query that relied on the `null` now fails and names both types; a guard earlier in the `AND` (`type.of(x) = 'DATE' AND …`) avoids the error, since `AND` short-circuits and an index scan hands other-kind values to the filter |
| The order of a pattern comprehension's list follows how the pattern was walked | Observed | Low: unspecified in Cypher too. A comprehension that pins a node through a `WHERE` or starts from its last node (see the support matrix) can list its matches in another order than a label scan did; sort the list when the order matters |
| `ORDER BY` after an aggregating or `DISTINCT` projection reads only its columns | Observed | Low: a key over the grouping keys (`ORDER BY c DESC, n.key` after `WITH n, count(m) AS c`) sorts by it; a key reading anything else from before the projection is a compile error. Through 0.24.1 both were evaluated on rows where the earlier variables no longer existed, gave `null` for every row, and the result came back unsorted without a word (`lora-database/tests/order_by_grouping_key_parts.rs`) |
| A pattern on a variable bound to `null` | Fixed | A pattern comprehension or `EXISTS { }` read a null variable as unbound and matched the pattern for every node in the graph (a signed-out "the viewer's genres" answered everybody's); `MATCH` on the same null failed instead of returning no rows. A null now matches nothing everywhere (`lora-database/tests/null_pattern_variables.rs`) |
| A map projection of `null` | Fixed | `null {.key}` answered `{key: null}` (`{}` for `.*`), so a missing node projected as a map of nulls: a lora-graphql `@cypher` field returning `head([...])` of an empty list read as an object with null fields and broke its non-null keys (G-52). It is now `null`, as in openCypher (`lora-database/tests/projection.rs`) |
| Dynamic property access on a node or relationship read `null` | Fixed | `n[k]` and `r[k]` answered `null` for a property that is there, where openCypher reads it as `n.k`; only lists and maps were indexed. They now read the property; a null or non-string key is still `null` (`lora-database/tests/projection.rs`) |
| Variable-length undirected traversal does not guard against reciprocal edges | Inferred | Low — visited-node tracking avoids repeats |

## Security

| Issue | Classification | Risk |
|-------|---------------|------|
| lora-graphql: `isViewer` with no viewer is false, not unknown | Changed | Low, by design (G-53). Through 0.25.2 `isViewer` without the claim was unknown like any claim test, so `none: { isViewer: true }` and `NOT { isViewer: true }` denied a signed-out reader every row. No node is the viewer then, so the test is false: `none` / `NOT` over it hold, a bare `isViewer` or `some` still admits nothing. A schema that used `NOT isViewer` to keep anonymous callers out must say so with a claim test or `@authentication` (`lora-graphql/test/auth-viewer.test.ts`, `consumer-regressions.test.ts`) |
| lora-graphql: the access matrix read a `$context` comparison as `denied` | Fixed | Low (G-54): the matrix has no request context, so the rule compiled as a missing value and read `denied` for every caller. It now reads `filtered`; at run time a request without the value still fails closed |
| lora-graphql: a `@cypher` mutation that only read a `@uniqueTogether` type was checked as writing it | Fixed | Low (G-55): any mention of the type's label or constrained relationship, even in a `MATCH` or a pattern comprehension, made the model warn and the mutation scan every node of the type afterwards. Only write clauses, and the variables they write that the statement binds to the type, count now; a `DETACH DELETE` of a node on a constrained relationship counts too, which the text match missed (`lora-graphql/test/unique-together.test.ts`) |
| lora-graphql: an upsert row that changes nothing is not written | Changed | Low (G-57): the comparison could tell a caller whether a guessed value is stored, so only fields any reader of the node may read are compared; a write-only, masked or `READ`-guarded field, a nested create, a polymorphic or rule-bearing relationship and `@populatedBy` keep the row on the write path, and the type's `UPDATE` rules are evaluated on the unchanged node. A mutation that wrote nothing no longer reaches `onWrite` (`lora-graphql/test/consumer-regressions.test.ts`) |
| lora-graphql: a `count` relationship filter cost tens of times what `totalCount` does | Fixed | Low (G-59): the distinct count folded the related nodes with `reduce`, comparing each one with every node before it and copying the list at each step, so `count: { gt: 0 }` over 200 related nodes per parent took 47x the `totalCount` of the same rows. A bound that only asks whether there are any (`gt: 0`, `gte: 1`, `eq: 0`, `lt: 1`, `lte: 0`) now counts relationships, since there are related nodes exactly when there are relationships; other bounds count `list.unique` of the node ids, which the engine dedupes in linear time (`lora-graphql/test/consumer-regressions.test.ts`, `lora-database/tests/builtin_namespaces.rs`) |
| A named database kept its whole WAL | Changed | Medium: `sync()` wrote a base snapshot but kept every segment since the database was created, so the `.loradb` carried the whole write history (749 MB of WAL beside a 94 MB snapshot for 3M nodes) and every open and archive rewrite read it. `sync()` now drops the segments its snapshot covers once the snapshot is beside the WAL, before the container is rewritten. A change feed resuming from before the last `sync()` fails with `LORA_CHANGES_TRUNCATED`, as after a managed checkpoint; after it, history replays over the container's snapshot (`lora-database/tests/wal.rs`, `change_feed.rs`) |
| A named database's `sync()` and open held the graph several times over | Fixed | **High** for large graphs (G-70): `sync()` decoded every record into a payload, then built the columns, the body, the envelope and the container frame in memory, and the container kept the snapshot resident after every call; opening read and decoded the snapshot the same way. On 3M nodes (a 630 MiB graph) `sync()` peaked 5.5 GiB over the graph and open 6.2 GiB. The snapshot now streams: the encoder walks the graph once per column, the decoder hands each record to the graph as its values arrive, and the container keeps the snapshot as `snapshot.lsnap` beside the WAL and streams it in and out. `sync()` peaks 12 MiB over the graph and open 48 MiB, repeated syncs keep RSS flat, and writers no longer wait while the snapshot is written (`lora-snapshot/src/graph_tests.rs`, `lora-database/tests/wal.rs`, `lora-database/examples/sync_memory_probe.rs`) |
| A named database's open and `sync()` still held the graph twice through Node | Fixed | **High** for large graphs (G-70, follow-up on 0.30.0): (1) a container rewrite read each WAL segment whole and gzipped it in memory, and one transaction never spans segments, so 2M nodes written in one statement left a segment every `sync()` copied through memory again (+300 MB per call); segment frames now stream. (2) Replay buffered each transaction decoded until its commit: that open peaked at 1281 MB RSS for a 158 MB graph. Replay now buffers 4 MiB and applies the rest provisionally over a copy-on-write clone (`lora_wal::ReplayStep`): 188 MB. (3) glibc arenas, and jemalloc during its decay period, kept what open, sync and close freed: Festimap's script scaled to a 2.3 GB graph held 2.4 GB after `dispose()` and 4.5 GB after reopening, and `sync()` crept +10 MB per call. Open, sync and close now return freed memory (`malloc_trim(0)`, or the `mallctl` purge under a preloaded jemalloc): 86 MB after dispose, reopen 2.36 GB (glibc) / 2.28 GB (jemalloc), peak within 1 MB of resident, `sync()` flat (`lora-database/tests/open_memory.rs`, `tests/wal.rs::replay_withdraws_a_large_transaction_it_applied_in_parts_without_a_commit`, `lora-wal/src/wal/tests.rs`, `examples/sync_memory_probe.rs records`) |
| No online backup of a directory-backed database | Fixed | **High** for deployments whose process owns its directory (G-62): a copy of a live directory is not a database, and the directory lock stops a second process. `Database::snapshot_to_dir`, `db.snapshot(targetDir)` and `LoraGraphQL.snapshot()` write `<target>/<name>.loradb` as of one committed transaction while reads and writes run, and return its size and LSN. Writers wait only for the WAL fsync and the graph handle. The file is written under a temp name, fsynced and renamed, so a kill leaves no partial container. Also `db.checkpoint()`, and `lora snapshot <dir> <target>` for a closed directory, which refuses a locked one. 10M nodes: 7.8 s; +55 MB with a writer committing 32k transactions meanwhile, slowest write 17 ms. Open: full copy each time; not exposed in Python, Ruby, Go, FFI or WASM (`lora-database/tests/directory_snapshot.rs`, `lora-node/test/snapshot_dir.test.ts`, `lora-graphql/test/snapshot.test.ts`) |
| A small node cost about 600 B resident after an open | Partly fixed | **Medium** (G-64): a keyed node (58-byte key, a hash, two integers, UNIQUE key) cost 610 B RSS per node after an open at 50k nodes and 456 B at 200k in 0.30.0 (Festimap's probe, macOS arm64). The hash index keeps a 64-bit digest and the entity id instead of a copy of a value one entity holds, confirmed against the record; a key's few repeated short strings are stored by dictionary number; replay checks a transaction where it reads it and decodes it one event at a time when it applies it; on macOS large WAL frames are read into pages unmapped after use. 0.32.0, same probe: 352 B at 50k and 280 B at 200k; the ten-property record with two relationships 1,145 to 531 B at 50k and 829 to 543 B at 200k; a fifth property costs 0-3 B. Bulk create 24% faster, key changes 35% faster, lookups unchanged, replay CPU +3-4%. Still open: 352 B at 50k against a 300 B target. The open's fixed 3.8 MB (mostly code pages) is 77 B of it, and the sorted index's 80-byte copy of the key remains; sharing it with the record cost 20% on key lookups and was not kept (`lora-database/tests/node_memory.rs`, `lora-store/src/memory/property_index.rs` and `dict.rs` tests, `lora-wal/src/codec/tests.rs::check_matches_decode`, `lora-database/examples/node_memory_probe.rs`) 0.33.0: `CREATE CONSTRAINT … IS UNIQUE OPTIONS { indexProvider: 'hash' }` backs a uniqueness or key constraint with the hash index alone, without the sorted copy of the key, for keys that only take lookups (Festimap's extraction graph). `node_memory_probe` (release, macOS arm64, WAL replay, 200k / 400k nodes), RSS per node: phase-3 record 274 / 298 B range-backed, 157 / 183 B hash-backed; phase-1 record 541 / 535 B and 429 / 409 B. Live heap per node is flat with size (218 and 104 B for phase 3); the RSS above it is malloc fragmentation from the replay, which `malloc_zone_pressure_relief` did not reduce (tried, not kept). Still open: the default range backing's ~110 B sorted copy of each key (sharing prefixes in the sorted index, without slowing key lookups), `lora-database/tests/hash_backed_constraints.rs`, `tests/node_memory.rs::a_hash_backed_key_costs_no_sorted_copy` |
| A list-membership filter (`$v IN n.list`, GraphQL `includes`) used no index | Fixed | Medium (G-63): `$g IN e.genreLineage` was a label scan plus a filter even with a RANGE index on the list (171 ms at 500k events). A RANGE index now also keeps each list by its distinct elements; `value IN n.list` and `any(x IN n.list WHERE x = value)` seek them (`NodeByPropertyScan` with `mode: element`, `RelByListElementScan` for relationships), costed by entities per element, so a more selective indexed test still wins. 500k: 170.6 to 5.3 ms. lora-graphql infers the index for INCLUDES (`lora-database/tests/list_element_seek.rs`, `lora-store/src/memory/sorted_property_index.rs`, `lora-node/test/explain_profile.test.ts`, `lora-graphql/test/list-includes-seek.test.ts`) |
| A range seek over list or boolean values returned no rows | Fixed | Medium (found during G-63): with a RANGE index, `n.tags > ['a']` or `n.flag > false` read the candidates from the index, then dropped every one in the re-check, which compared only strings, temporals, durations and numbers; the unindexed filter returned them. Lists and booleans now compare as the operators do (`lora-database/tests/list_element_seek.rs`) |
| An OR of list-membership filters scanned the label | Fixed | Medium (G-72): `$g IN e.genreLineage OR $h IN e.genreLineage` and `any(x IN $gs WHERE x IN e.genreLineage)` were a label scan though one such test seeks (G-63), so a multi-genre filter cost the whole label and lora-graphql refused it on artists past ~35k. An OR whose every branch is an element test on one RANGE-indexed list, and both `any()` forms over a value list, now seek once per distinct value and return each node once (`mode: any-element`, nodes and relationships); the filter stays above the seek. lora-graphql adds `includesAny` and an OR of `includes` on one list seeks the same way. An OR across properties still scans (`lora-database/tests/list_element_seek.rs`, `lora-graphql/test/list-includes-any.test.ts`) |
| lora-graphql: a filtered `totalCount` was charged the whole label | Fixed | Medium (G-73): a count under any non-key filter was estimated at the label (100k nodes for one `includes` seek on 100k, 200k for an OR of two), so a selective filtered count on a large type was refused, and a `@cypher` root without `cost:` was charged only its projection. `analyze()` now keeps per-value counts of every `EQ`/`IN`/`INCLUDES` field (exact up to 1,024 values, else the 64 most common and the largest of the rest): a seek is charged the nodes holding its values, an engine-seekable OR the sum, an AND its narrowest test; an OR the engine scans for still costs the label. A `@cypher` root without `cost:` is charged its statement's largest plan estimate. On a skewed 6,000-node graph every estimate is at or above the true count and within 2× of it (`lora-graphql/test/value-statistics.test.ts`) |
| Reopening a named database right after `dispose()` in the same process found it locked | Fixed | Medium (Festimap's G-71 for `dispose()`, not the replay item above): `dispose()` dropped the handle's reference while a running query or a change feed's delivery still held the engine, and the engine released its directory lock only after its WAL and container closed on that thread. An open in that window found no live engine to share and failed with `LORA_LOCKED` (about 1 reopen in 4 in Festimap's repro). Each lock now leaves a process-wide table only once the OS lock is released, an open that finds no live engine waits for this process's own closing one (up to 60 s; another process's lock still fails at once), and `close(): Promise<void>` (also `await using`) resolves once the handle's operations have settled and the directory is unlocked. Queries already running finish rather than being cancelled (`lora-node/test/close.test.ts`: 40 rounds by default, 1,000 with `LORA_CLOSE_ROUNDS=1000`; `lora-database/tests/named_release.rs`) |
| `date({timezone: $tz})` was an error | Fixed | Low (G-61): "`timezone` is not a component of DATE" forced the `date(datetime({datetime: datetime(), timezone: $tz}))` detour for the reader's local day. A map of only a `timezone` is now the current value in that zone for every temporal type, as in Neo4j (`lora-database/tests/temporal_constructors.rs`) |
| No awaitable WAL flush: the only durability point was `sync()`, a checkpoint | Fixed | Medium (G-74): a writer that acknowledges durability to someone else had to call `sync()`, which writes a snapshot and scales with the graph (≈290 ms at 300k nodes, 14 s and 8.7 GB peak at Europe size; 164 of a 208 s promotion), or wait out the group-sync interval. `flush()` fsyncs the WAL only and resolves with its durable LSN: one fsync per call, none when nothing is new (`lora-database/tests/wal_flush.rs`, `lora-node/test/flush.test.ts`: every flushed write survives `kill -9`) |
| An equality on a key no node holds lost to a literal equality beside it | Fixed | Medium (G-75): with no distinct count for a key (no node of the label holds it), its equality was estimated at the whole label, so `MATCH (r:ReviewItem {proposalOf: k}) WHERE r.state = 'REJECTED'` per `UNWIND` row sought `state` and read half the label each time (300,000 rows for 200 keys; 1.86 s for 1,000 keys on Festimap's graph). Such an equality now estimates 0 rows, in the seek choice and in the pattern anchor alike: 1 ms (`lora-database/tests/planner_known_parameters.rs`) |
| Opening a named database replayed its whole WAL at once | Fixed | **High** for a long write history (G-71): replay read every committed event into one list before applying any, so an open held the decoded log beside the graph. Festimap's extraction container, 2.2 GB holding 10.3 GB of WAL and no snapshot, needed 35-50+ GB and never opened; each failed attempt left the extracted WAL behind for the next. Replay now applies each transaction as its commit is read, and an open that replays at least `compact_on_open_wal_bytes` (64 MiB) of WAL, more than a quarter of its snapshot, checkpoints before it returns, so the next open loads a snapshot. On 200k nodes rewritten 20 times the open peaked at 34 MiB over a 24 MiB graph instead of 1.2 GiB, and the second open took 0.3 s instead of 4.6 s (`lora-database/tests/open_memory.rs`, `examples/replay_memory_probe.rs`). The first open of such a container still extracts its WAL to disk before it replays it |
| Node `createDatabase()` opened on the JS thread | Fixed | Medium: the `async` function called a synchronous constructor, so reading the snapshot and replaying the WAL blocked the event loop for the whole open, health checks included. `createDatabase()` and `openWalDatabase()` now open on the libuv threadpool (`lora-node/test/open.test.ts`) |
| A failed automatic checkpoint after a WAL commit left the database unopenable | Fixed | **Critical**: the checkpoint error discarded the committed staged graph, the next write reused its ids and replay then failed with "node id N already exists". The checkpoint now runs after publish and only logs; its counter resets (`lora-database/tests/managed_snapshots.rs::failing_automatic_checkpoint_does_not_fail_or_lose_writes`) |
| Release builds aborted on panic | Changed | **High**: `panic = "abort"` made every binding's `catch_unwind` inert, so any engine panic killed the Node, Python, Ruby or Go host and the whole lora-server. Release now unwinds; a panic is a `LORA_INTERNAL` error for that call (wasm32 still aborts) (`lora-node/test/robustness.test.ts`, `lora-server/tests/limits.rs::engine_panic_answers_500_and_server_keeps_serving`) |
| Nested input made the parser backtrack exponentially or overflow the stack | Fixed | **Critical**: 14 nested parentheses took 3.7 s and 100 never finished; about 100 nested brackets, a 500-term `1+1+...` or a deeply nested parameter crashed the process. The grammar parses each construct once (typical queries parse 2.7x faster), and queries are limited to 64 levels of nesting, 256-deep operator chains and 256 clauses; values nest at most 128 deep and grow to at most 128 MiB (`lora-parser/tests/limits.rs`, `lora-database/tests/query_limits.rs`) |
| Builtins panicked or allocated without bound on plain input | Fixed | **Critical**: `math.clamp(5, 10, 1)`, `string.repeat('ab', 9e18)`, `number.format(1.5, 70000)` aborted the process; `string.pad`, `list.combinations` and string doubling took GBs and ignored the deadline. | Variable-length paths recursed without bound and ignored the deadline | Fixed | **High**: `*1..1000000` on a long chain overflowed the stack or ran 217 s at 16 GB under a 10 s timeout. | Range index lost rows when Int bounds met Float data | Fixed | **High**: Ints sorted below every Float, so `WHERE n.age > 25.5` on a RANGE index missed `age: 30`, and ORDER BY served from the index put all Ints first. | Mid-log WAL corruption was truncated as a torn tail; replay had no gap check | Fixed | **High**: one flipped bit silently dropped every later commit and destroyed the evidence; a log that no longer reached back to the snapshot fence replayed from the middle. Only a bad final frame of the newest unsealed segment is a torn tail (its bytes are kept as `.torn-<offset>`); anything else fails with `LORA_WAL_CORRUPTION`, as does a gap. `truncate_corrupt_tail` / `--wal-truncate-corrupt-tail` is the opt-in escape hatch (`lora-wal/src/wal/tests.rs`) |

## Performance

| Issue | Classification | Impact |
|-------|---------------|--------|
| Write publication still serializes | Observed | Read-only auto-commit queries load Arc snapshots without a store lock; write commits and explicit read-write transactions serialize through the database writer mutex |
| Writers waiting on the Node pool | Fixed | A read-write `begin()` transaction waited for the writer lock on a libuv worker, and each of its calls went through one; with more waiting transactions than pool threads, the lock holder could not run its next statement and the process stopped. Interactive transactions now wait and run on their own threads and settle their promises from there (`crates/bindings/lora-node/src/interactive.rs`, `test/pool.test.ts`). Auto-commit and batched writes waiting for the lock still occupy a pool thread (a latency, not a deadlock) |
| Node transaction lifecycle | Fixed | After the pool fix, a command queued behind a failed statement, a commit or a rollback never settled and kept the process alive; `begin()` after `dispose()` leaked a deferred; `dispose()` joined an actor still waiting for the writer lock, deadlocking the JS thread when two handles shared a directory; and a mutating `stream()` opened on the JS thread while a transaction held the lock deadlocked it. Uncalled completions now settle as closed, only idle actors are joined, and mutating streams run on their own thread (`lora-node/src/actor.rs`, `src/stream.rs`, `test/pool.test.ts`) |
| A statement the engine never ran closed a Node transaction without ending it | Fixed | `tx.execute()` / `executeMany()` given an already-aborted signal (a request cancelled between two statements), or options the binding refuses, rejected before the native call and marked the handle closed as if the engine had rolled back. The native transaction kept the writer lock with no handle left to release it, and every later write waited until the process restarted. A failed call now always rolls the native transaction back before it rejects, so `isOpen === false` means the lock is free (`lora-node/ts/index.ts`, `test/interactive.test.ts`, `lora-graphql/test/cypher-mutation-hardening.test.ts`). A write that gives up waiting for the lock says so (`query deadline exceeded waiting for the writer lock`), where it used to read like a statement that ran out of time |
| Mutating streams across bindings | Fixed | A mutating stream holds the writer lock until it is drained or closed, and its lock guard must be released on the thread that took it. In lora-ffi (and so lora-go) and lora-python, streams were pulled and freed on any thread, and every binding but Node dropped the database before a stream borrowing it (use-after-free: SIGSEGV when a stream outlived its database). Mutating streams now live on their own thread and drop before the database (`lora-ffi/src/stream.rs`, `lora-python/src/stream.rs`). That thread sends rows in chunks (up to 256 rows or about 50 µs) and commits only when the consumer asks past the last row, via `QueryStream::pull`/`finish`; a stream read to its last row but closed before the end rolls back |
| Waiting for the writer lock with the host lock held | Fixed | lora-python `stream()`/`clear()` waited for the writer lock with the GIL held, and `AsyncDatabase.stream` on the event loop, so a second writer froze the thread that could finish the first (process hang). lora-ruby `clear`/`close` held the GVL (a stall). Both now release it (`lora-python/tests/test_concurrency.py`, `lora-ruby/test/test_writer_lock.rb`) |
| lora-wasm writes during a write stream | Fixed | A write started while a write stream held the writer lock panicked (`RuntimeError: unreachable`: wasm32's mutex cannot wait). It now fails fast with `LORA_TRANSACTION`; reads keep working (`lora-wasm/src/writer.rs`, `test/single-thread.test.ts`) |
| Parked mutating streams in fixed pools | Observed (caller contract) | The libraries never wait for another caller thread, but a host that parks an open mutating stream and queues its next pull behind writers in a fixed pool (a C thread pool, a saturated Python executor) can starve it. Documented in `lora_ffi.h`, the Go and Python READMEs |
| Go waiting writers | Observed | Each write waiting for the lock holds an OS thread, not a P, so writers cannot deadlock at `GOMAXPROCS=1`; more waiting writers than `debug.SetMaxThreads` abort the process (`lora-go/concurrency_test.go`) |
| lora-server slow requests | Observed | A current-thread runtime calling the engine synchronously cannot deadlock on the writer lock, but one slow query or admin snapshot blocks every request, `/health` included, with no server-side timeout (`lora-server/tests/concurrency.rs`) |
| Some predicates still scan | Observed | Vector similarity, regex, non-indexed properties, nested map paths, and unsupported composite seek shapes scan candidate records |
| Pattern subqueries are matched by the expression evaluator, not planned | Observed | A pattern comprehension, `EXISTS { }` or `COUNT { }` runs once per row of the operator that holds it and does not appear as operators in `explain()`. It finds an unbound node through an index for an inline property map and for a `WHERE` conjunct `v.key = value`, `v.key IN list` or `v.key STARTS WITH prefix`, and starts a chain from whichever end is bound or pinned (`pattern_seeks` in the operator's details names the properties). Through 0.24.1 only the inline map sought: the `WHERE` form scanned the label once per row (4.5 s against 0.7 ms with 30,000 nodes and 300 rows). Any other predicate, a range comparison included, still scans the label of an unbound node per row, and no statistics pick between two pinned ends (`lora-database/tests/pattern_subquery_where_seek.rs`) |
| Clone-heavy read API | Observed | Allocation overhead proportional to result set. Inside a query, a row slot holds a large value (a list, map or path with 8+ entries or a nested container, a long string, a binary or a vector) behind a shared pointer, so an operator that makes a row per candidate (expand, OPTIONAL MATCH, UNWIND, FOREACH, `CALL { }`, list constructs) no longer copies a list the row carries, a grouping, `DISTINCT` or `UNION` key over it is built once and compared by pointer, and a lone function argument (`size(big)`), a comparison, `coalesce`, `CASE`, a quantifier, a comprehension and `reduce` read it in place (`tests/carried_value_sharing.rs`). A map or list literal that wraps the list, a function with two or more arguments other than `coalesce`, and every returned row still copy it |
| Query timeout coverage | Observed | Cooperative deadlines and cancellation cover eager, streaming and write execution in Rust and the Node binding (`execute`, `transaction`, `stream`, `begin`), including loops inside one expression (pattern/list comprehensions, `reduce`, list quantifiers): a three-level nested relationship filter once ran 5-15 s past a 1 s deadline on the buffered read path and returned rows; it now fails at the deadline (`lora-database/tests/timeouts.rs`). A timed-out scan frees the rows it built on the rayon pool, so the error is not delayed by the deallocation (a cartesian read used to return 2-3x past its deadline). A `stream()` checks between rows, so one blocking pull (a large aggregation) finishes before the check. HTTP and the other bindings do not expose timeouts yet |
| Optimizer is still local | Observed | Cost-based index selection exists for scan/filter sites, and a single-key `ORDER BY` over a range-indexed property with a range predicate streams from the index. Every bound on the scanned property narrows the scan: two bounds the planner cannot order (parameters, or a `STARTS WITH` prefix and a `>` cursor) are both kept and the tighter one is picked per row. Through 0.26.2 the second was left to the filter, so a keyset page within a prefix seeked from the prefix and read every earlier page (E-8; `lora-database/tests/range_scan_bound_intersection.rs`). WHERE conditions are pushed down to the scan of the variable they test (so `n.key = $k` and `n.key IN $list` seek on any node of a pattern), a chain starts from its cheaper end, and an unfiltered `count(n)` over one label reads the label count. `ORDER BY … LIMIT` (literal or parameter) keeps only `skip + limit` rows instead of sorting every match. No join ordering or global cardinality search; an index-ordered scan is not yet chosen when the filter is not selective |
| Staged writes share structure | Observed | Writes the in-place fast path cannot prove failure-free (relationship `CREATE`, `MERGE`, `SET` from an expression, anything with a deadline) run on a copy of the graph so a failure leaves nothing behind. The copy is structural: node and relationship slots, adjacency lists and label indexes are two-level copy-on-write radix trees (`ChunkedVec`), the index and constraint catalogs and every secondary index (hash, range, text, point, full-text) are shared and copied on write: hash buckets are a persistent hash trie, range partitions and posting lists are grouped chunk tables. Cloning the graph is O(1): about 0.3 µs at 2M nodes / 8M relationships, against 218 µs when the slabs were flat chunk tables. A write copies only the bounded path it touches, so its cost no longer grows with the graph. At that size a staged `SET` takes about 11 µs, a `CREATE` on a constrained label about 15 µs, `graph_create_node` of a node with an indexed unique `id` about 16 µs and a relationship `CREATE` about 55 µs (240–430 µs before; `tests/write_scaling.rs`, `examples/storage_baseline.rs`) |

### Memory per element

Measured with a counting allocator (`cargo run --release -p lora-database
--example heap_probe`); live heap only, so process RSS adds allocator
overhead on top.

| Element | Bytes |
|---------|-------|
| Node, no properties, one label | ~80 |
| Each property on a node or relationship | 2 for the key and kind, plus the value: 1-10 for an integer, 8 for a float, its length plus 1-2 for a string. Lists, maps, temporals, points and vectors are stored in the snapshot codec's form |
| Relationship, no properties | ~35 to ~55. The higher figure applies once its endpoints have more than two relationships each: their adjacency entries (8-10 bytes each, two per relationship) then live on the heap |
| Unique-valued entry in a RANGE index or uniqueness constraint | ~140 (about 90 for the exact-match half, 50 for the sorted half) |
| 20k festivals + 5k users + 100k relationships, no declared indexes | ~112 per element |
| Same, with two uniqueness constraints, a full-text and a point index | ~175 per element |

Records are stored encoded: labels, relationship types and property keys as
small numbers from per-graph dictionaries, values in as few bytes as they
need. With records this small, declared indexes are a large share of an
indexed graph's memory: a unique key adds about twice what its node's record
takes.

### Process memory after reopening a database

A process that only opens an existing database can show more RSS than the
process that wrote it, while holding the same data in less memory. Measured
on macOS arm64 through `@loradb/lora-node` 0.24.0, on 20k + 5k nodes, two
property indexes and 100k relationships with one property each, loaded in
`UNWIND` batches of 1,000 into a named database and reopened in a fresh
process (`vmmap -summary` for the allocator's own figures):

| | Writer | Reopened |
|---|---|---|
| RSS growth (`process.memoryUsage().rss`, after `gc`) | 38.5 MB | 57.5-58.4 MB |
| Bytes allocated in the malloc zone | 18.2 MB | 16.5 MB |
| Dirty pages in the malloc zone | 46.8 MB | 25.7 MB |
| Physical footprint of the process | 73.1 MB | 52.0 MB |
| Engine live heap, same element count (`storage_baseline restart`) | 16.4 MB | 16.4 MB (snapshot), 16.5 MB (WAL replay) |

The reopened graph is the same size or smaller. What differs is the path
there: opening replayed the WAL, which then read every committed event into
memory before applying it (since fixed, G-71: replay now applies each
transaction as it reads its commit), so the process touched about three
times the memory it ends up holding (inferred from the zone's resident pages, 58 MB
against 16.5 MB allocated; the peak itself was not traced). It frees the
difference, and macOS keeps freed
pages in RSS until something else needs them. RSS therefore reports the
replay's high-water mark, not what the database holds; the physical
footprint, which is what macOS charges the process, is lower after a reopen
than after a load.

Two things follow. Compare processes by allocated bytes or footprint, not
RSS. And size a container for the replay's peak, not for the steady state:
the transient is real while it lasts.

Declaring indexes and constraints before a bulk load keeps the load
linear: a uniqueness check looks the value up in its backing index rather
than scanning the graph. For the largest loads, creating indexes after
the load is still somewhat faster because the index is built in one pass.
